# 03 — გემიფიკაცია და მინი-თამაშები

## 1. პრინციპები

1. **ოსტატობა, არა იღბალი.** შედეგი დამოკიდებულია მოთამაშის მოქმედებაზე. არანაირი „ბორბლის დატრიალება“ ფულის სანაცვლოდ, არანაირი ფარული „დატრიალებული“ შანსები. (ბავშვთა აუდიტორია + სამართლებრივი რისკი.)
2. **ყოველთვის უფასო, ყიდვა არ არის პირობა.**
3. **მოკლე:** ერთი რაუნდი 20–60 წამი. მობილურზე ერთი თითით სათამაშო.
4. **თამაში პროდუქტის შესახებაა:** თამაშში ჩანს იმ სათამაშოს ფოტო/ფერები, რაზეც ფასდაკლება ითამაშება → თამაში თავისთავად რეკლამაა.
5. **ფასდაკლება სერვერზე იბადება.** კლიენტი მხოლოდ მოქმედებების ჩანაწერს აგზავნის; სერვერი ამოწმებს და წყვეტს.
6. **ადმინი მართავს ყველაფერს კოდის გარეშე:** რომელი თამაში, რომელ პროდუქტზე, რა სირთულით, რამდენი პროცენტი, რამდენჯერ, რა ვადით, რა ბიუჯეტით.
7. **ფასდაკლების ბიუჯეტი დაცულია:** ჯამური ზღვარი, რომლის მიღწევისას კამპანია ავტომატურად ჩერდება.

## 2. თამაშების კატალოგი

ყველა თამაში — ორიგინალი, ZoyToy-ს საკუთარი ვიზუალით (ცნობილი ჟანრები, არა კონკრეტული არსებული თამაშების ასლები).

**რატომ ეს სამი MVP-ში:** სამივე თითქმის **არ საჭიროებს დამატებით ასეტს თითოეულ პროდუქტზე** — ადმინი
ირჩევს პროდუქტს, ფოტო ავტომატურად შედის თამაშში. ეს ნიშნავს, რომ ახალი კამპანიის შექმნა წუთებია და არა დიზაინერის სამუშაო დღე.

## 3. თამაშის მოდულის ინტერფეისი (`packages/games`)

ყოველი თამაში — დამოუკიდებელი მოდული ერთნაირი კონტრაქტით. საიტმა არაფერი იცის თამაშის შიგნით, მხოლოდ ამ ინტერფეისის.

```ts
// packages/game-protocol
export interface GameModule<C> {
  key: string                       // "toy-drop"
  version: string                   // ვერსია — სესიაში ინახება, რომ ვალიდაციამ სწორი წესები გამოიყენოს
  configSchema: z.ZodType<C>        // ადმინის ფორმაც ამ სქემიდან იხატება
  presets: Record<'easy'|'medium'|'hard', C>
  assets(config: C, skin: Skin): AssetManifest        // რა უნდა ჩაიტვირთოს წინასწარ
  mount(el: HTMLElement, ctx: GameContext<C>): GameInstance   // მხოლოდ ბრაუზერში
  verify(input: VerifyInput<C>): VerifyResult                 // სუფთა ფუნქცია — სერვერზე ეშვება
}

export interface GameContext<C> {
  config: C; seed: string; skin: Skin; locale: 'ka' | 'en'
  reducedMotion: boolean; sound: boolean
  onEvent(e: InputEvent): void      // ყოველი მოქმედება ჩაიწერება (დრო + მონაცემი)
  onFinish(r: { score: number; durationMs: number }): void
}

export interface VerifyInput<C> { config: C; seed: string; events: InputEvent[]; claimedScore: number; durationMs: number }
export interface VerifyResult   { valid: boolean; recomputedScore: number; flags: string[] }
```

**მთავარი ხრიკი — დეტერმინიზმი:** ყველა შემთხვევითობა (სად ჩამოვარდება სათამაშო, ბარათების განლაგება, ფაზლის არევა)
გენერირდება **სერვერის მიერ მოცემული `seed`-იდან**. ამიტომ სერვერს შეუძლია მოთამაშის მოქმედებების ჩანაწერი
**თავიდან „გაითამაშოს“** (replay) და დამოუკიდებლად გამოთვალოს ქულა. თუ კლიენტის ქულა და სერვერის ქულა არ ემთხვევა → `rejected`.

| თამაში | რა იგზავნება | როგორ მოწმდება |
|--------|-------------|----------------|
| Memory | გადაბრუნებების თანმიმდევრობა + დრო | ბარათების განლაგება seed-იდან → თანმიმდევრობის ლოგიკურობა, სვლები, დრო |
| Puzzle | სვლების სია | საწყისი არევა seed-იდან → სვლების გამოყენება → დასრულებულია? სვლები/დრო |
| Toy Drop | კალათის პოზიცია დროის მიხედვით (შეკუმშული, ~20 წერტილი/წმ) | სიმულაცია seed-ით იგივე ფიქსირებული ბიჯით (fixed timestep) → დაჭერილების დათვლა |

ამიტომ თამაშის ფიზიკა/ლოგიკა იწერება **ფიქსირებული დროის ბიჯით** და **ცალკე რენდერისგან** (logic ↔ render გაყოფა),
რომ იგივე კოდი ბრაუზერშიც და სერვერზეც (Node) ერთნაირად გაეშვას.

## 4. სესიის ნაკადი და თაღლითობისგან დაცვა

```
 კლიენტი                                           სერვერი
   │  POST /api/games/session {campaign}              │
   │ ───────────────────────────────────────────────▶ │ შემოწმება: კამპანია აქტიურია? ლიმიტები? ბიუჯეტი?
   │                                                  │ ქმნის GameSession: seed, startedAt, ვერსია
   │ ◀─────────────── {sessionId, seed, config, token}│ token = HMAC(sessionId, ვადა 10 წთ), ერთჯერადი
   │                                                  │
   │  … თამაში (მოქმედებები ჩაიწერება) …              │
   │                                                  │
   │  POST /session/:id/finish {events, score, token} │
   │ ───────────────────────────────────────────────▶ │ 1. token ვალიდურია, ჯერ არ გამოყენებულა
   │                                                  │ 2. ხანგრძლივობა: სერვერის დრო (finish − start) ≈ თამაშის დრო
   │                                                  │ 3. module.verify() → replay → ქულა ემთხვევა?
   │                                                  │ 4. ადამიანურობა: რეაქციის დროები, მოქმედებების რიტმი
   │                                                  │ 5. ტიერის განსაზღვრა → Reward (თუ შესაძლებელია)
   │ ◀──────────────── {verdict, score, tier, reward?}│
```

| უსასრულო ცდები | `attemptsPerDevicePerDay` (მაგ. 3) + IP-ის ჰეშის ლიმიტი; სცადე ხვალ |
| კუპონის გაზიარება | ჯილდო გამოყენებისას მიება **დადასტურებულ ნომერს**; სხვა ნომრით ვეღარ გამოიყენება |
| ფასდაკლებების დაგროვება | ერთ შეკვეთაზე მაქს. ერთი თამაშის ჯილდო; სხვა კუპონებთან დაგროვება — გლობალური პარამეტრით (ნაგულისხმევად არა) |
| ბიუჯეტის გადაჭარბება | `totalRewardBudget` / `maxRedemptions` → კამპანია ავტომატურად `paused` + ადმინს შეტყობინება |

> არცერთი დაცვა არ არის 100%-იანი, მაგრამ ეს ფენები ერთად თაღლითობას **მოგებაზე ძვირს** ხდის — ეს არის მიზანი.
> საეჭვო სესიები ჩანს ადმინში და შეიძლება ხელით დადასტურდეს/გაუქმდეს.

## 5. ჯილდოს წესები

- **მხოლოდ ყიდვაზე.** თამაშის ჯილდო ქირაზე არ ვრცელდება (გადაწყვეტილება #15).
- **გლობალური მაქსიმუმი — 50%** (გადაწყვეტილება #13). ცალკეული კამპანიის ზღვარი ≤ 50%. ადმინი გაფრთხილებას ხედავს, თუ კამპანია 30%-ს აჭარბებს: „დარწმუნდი, რომ ამ ნივთებზე მარჟა ამას უძლებს“.
- **ტიერები:** რეკომენდებული სტრუქტურა — ფართო ქვედა საფეხურები და იშვიათი მაღალი:
  `≥ 150 ქულა → 10%`, `≥ 300 → 20%`, `≥ 450 → 30%`, `≥ 600 → 50%` (უკანასკნელს მხოლოდ საუკეთესო მოთამაშეების ~2–5% აღწევს).
  ადმინი ხედავს ქულების განაწილების ჰისტოგრამას და იცის, რა წილი აღწევს თითოეულ საფეხურს.
- **უნიკალური ნივთის პრობლემა:** მეორადი ნივთი ხშირად ერთადერთია. თუ კამპანია ერთ კონკრეტულ ნივთზეა და ის გაიყიდა
  (მაგ. სხვამ იყიდა ან მაღაზიაში გაიყიდა) — კამპანია **ავტომატურად სრულდება**, ხოლო უკვე მოგებული ჯილდოები
  **გადაიქცევა იმავე კატეგორიის ჯილდოდ** (მოგებული პროცენტით, იგივე ვადით), რომ მომგებს იმედი არ გაუცრუვდეს.
  ამიტომ რეკომენდაცია: კამპანიები უფრო ხშირად **კატეგორიაზე/ფრენჩაიზზე/ნივთების ჯგუფზე** იყოს, ვიდრე ერთ ნივთზე.
- **საუკეთესო შედეგი ითვლება:** ერთ კამპანიაზე მომხმარებელს აქვს **ერთი აქტიური ჯილდო**. თუ ხელახლა ითამაშებს და უკეთეს ტიერს მიაღწევს — ჯილდო **განახლდება** (არ ემატება). ეს ხალისიანია („გააუმჯობესე შედეგი!“) და ბიუჯეტსაც არ ზრდის.
- **ვადა:** `rewardValidityHours` (მაგ. 48 სთ) — ქმნის ბუნებრივ, **ნამდვილ** სიჩქარეს (არა ყალბ ტაიმერს).
- **სფერო:** მხოლოდ კამპანიის სამიზნე ნივთებზე/კატეგორიებზე, მხოლოდ ყიდვაზე.
- **ზღვრები:** `maxDiscountPercent` (≤ 50%) და არჩევითად `maxDiscountAmount` (მაგ. მაქს. 50 ₾), `minOrderTotal`.
- **რეგისტრაციის გარეშე თამაში** (გადაწყვეტილება #14):
  1. ნებისმიერი თამაშობს, ანგარიშის გარეშე.
  2. მოგებისას ჯილდო ინახება **მოწყობილობაზე** (სერვერზე ჩანაწერი + ბრაუზერში ხელმოწერილი გასაღები), ვადით.
     ეკრანზე: „−20% შენთვის შენახულია 48 საათით“.
  3. checkout-ზე ჯილდოს გამოსაყენებლად — **ტელეფონის დადასტურება SMS კოდით**. ეს ავტომატურად ქმნის ანგარიშს (პაროლის გარეშე) და ჯილდო ამ ნომერს მიება.
  4. თუ ამ ნომერს ამ კამპანიაზე ჯილდო უკვე აქვს გამოყენებული → „ამ კამპანიაში ფასდაკლება უკვე გამოიყენე“ (დაგროვება არ ხდება).
  - ხარვეზი, რომელსაც ვიღებთ: ბრაუზერის მონაცემების წაშლისას გამოუყენებელი ჯილდო იკარგება. ამიტომ მოგების ეკრანზე არჩევითი ღილაკი: „შეინახე ნომერზე ახლავე“ (იგივე SMS კოდი).
- **კალათაში:** მოგებული ჯილდო ავტომატურად ჩანს კალათაში, როგორც „🎮 თამაშით მოგებული −10%“ — ფასის ანიმირებული შემცირებით.

## 6. ადმინის მართვა

(სრულად — [04](04-admin-panel.md#თამაშები-და-ფასდაკლებები).) კამპანიის შექმნის ოსტატი 5 ნაბიჯით:
1. **თამაში** — ბარათებიდან არჩევა (ანიმირებული პრევიუთი).
2. **სამიზნე** — ნივთები / კატეგორიები / ფრენჩაიზები / ასაკი; ჩანს, რამდენი ნივთია ამჟამად მარაგში ამ სამიზნეში.
3. **სირთულე და გარეგნობა** — პრესეტი, ფონი, მუსიკა; **„ითამაშე პრევიუში“** ღილაკი (ადმინს შეუძლია თავად სცადოს, ჯილდოს გარეშე).
4. **ჯილდოები** — ტიერები, ზღვრები, ვადა, ლიმიტები, ბიუჯეტი.
5. **განრიგი** — დაწყება/დასრულება, კვირის დღეები; სტატუსი draft → active.

## 7. ანალიტიკა (ადმინის დაფაზე)

- თამაშები: დაწყებული / დასრულებული / უნიკალური მოთამაშე, საშუალო ხანგრძლივობა
- ქულების ჰისტოგრამა ტიერების ზღვრებით
- ჯილდოები: გაცემული / გამოყენებული / ვადაგასული; **ფასდაკლების ფაქტობრივი ხარჯი ₾-ში**
- **ბიზნესის შედეგი:** შეკვეთები ჯილდოთი, მათი შემოსავალი, კონვერსია „მოთამაშე → მყიდველი“ vs. „არამოთამაშე → მყიდველი“
- საეჭვო სესიები (სია, მიზეზებით)

## 8. UX ნაკადი მომხმარებლისთვის

1. **აღმოჩენა:** პროდუქტის ბარათზე — მოძრავი ბეჯი „🎮 ითამაშე −50%-მდე“; პროდუქტის გვერდზე — თამაშის ბარათი;
   ცალკე გვერდი `/play` — ყველა აქტიური კამპანია („სათამაშო მოედანი“).
2. **შესავალი ეკრანი:** მასკოტი ხსნის წესებს 1 წინადადებით + ანიმირებული მინიშნება; ჩანს ტიერები („300 ქულა = −20%“) და დარჩენილი ცდები.
3. **თამაში:** სრულეკრანიანი (მობილურზე), ხმა გამორთულია ნაგულისხმევად, ღილაკით ირთვება; პაუზა.
4. **შედეგი:** ქულის ანიმირებული დათვლა → ტიერის „გახსნა“ (კონფეტი, მასკოტის ზეიმი) → ჯილდოს ბარათი ვადით („შენთვის შენახულია 48 სთ“) →
   ორი ღილაკი: **„დაამატე კალათაში ფასდაკლებით“** (მთავარი) და „სცადე ხელახლა“ (თუ ცდა დარჩა).
5. **წაგებისას:** არა „წააგე“, არამედ „კინაღამ! კიდევ 40 ქულა −10%-მდე“ + მასკოტის მხარდამჭერი ანიმაცია.

## 9. ხელმისაწვდომობა თამაშებში

- ყველა თამაში იმართება შეხებით, მაუსით **და** კლავიატურით.
- `prefers-reduced-motion` → ნაკლები ვიბრაცია/ციმციმი, კონფეტის გარეშე.

- ციმციმი ≤ 3-ჯერ წამში (ეპილეფსიის რისკის თავიდან ასაცილებლად).
